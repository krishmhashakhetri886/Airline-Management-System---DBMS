2) AUTH MODULE QUERIES
====================================================
File: backend/routes/auth.js

Route: POST /signup

Q1
SELECT passenger_id FROM Passenger WHERE email_id = ? LIMIT 1

Why used
- Email uniqueness check before insert.

How used
- Executed inside transaction.
- If row exists, rollback + 409 conflict.

DBMS concepts
- Predicate filter by unique candidate key (email_id)
- LIMIT 1 for early stop/efficiency

Q2
SELECT COALESCE(MAX(passenger_id), 0) + 1 AS next_passenger_id FROM Passenger

Why used
- Manual passenger_id generation.

How used
- Reads current max id, increments by 1, uses result in insert.

DBMS risks/notes
- Potential race condition in high concurrency if not protected by stronger locking/sequence.
- Here it runs in transaction, but MAX+1 can still conflict under concurrent transactions.

Q3
INSERT INTO Passenger (
  passenger_id, first_name, middle_name, last_name,
  email_id, phone_no, dob, passport_no, password
) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)

Why used
- Creates new passenger account.

How used
- Executed after validation + duplicate check.
- Commit on success; rollback on error.

Route: POST /login

Q4
SELECT * FROM User WHERE email = ? AND password = ?

Why used
- Admin authentication lookup.

How used
- Checked first; if found returns admin session payload.

Q5
SELECT * FROM Passenger WHERE email_id = ? AND password = ?

Why used
- Passenger authentication fallback if admin lookup fails.

How used
- Returns passenger user payload with role="passenger".

Security note
- Password appears compared as plain value in SQL.
- DBMS works, but production best practice is hashed password storage and compare in app layer.

Q17
SELECT
  b.booking_id,
  b.amount,
  b.status,
  f.source,
  f.destination,
  f.source_terminal,
  f.destination_terminal,
  f.departure_time,
  f.arrival_time,
  sa.name AS source_airport_name,
  sa.city AS source_city,
  da.name AS destination_airport_name,
  da.city AS destination_city,
  al.name AS airline_name
FROM booking b
JOIN flight f ON b.flight_id = f.flight_id
JOIN airport sa ON f.source = sa.airport_code
JOIN airport da ON f.destination = da.airport_code
JOIN aircraft ac ON f.aircraft_id = ac.aircraft_id
JOIN airline al ON ac.airline_id = al.airline_id
WHERE b.passenger_id = ?

Why used
- Builds rich My Bookings payload with terminals, city, airport names, airline.

How used
- Single join query instead of multiple API calls.

DBMS concepts
- Multi-table equi-joins
- Projection aliases for frontend-friendly field names

Route: POST /cancel-booking/:booking_id

====================================================
7) DBMS PATTERNS USED ACROSS PROJECT
====================================================
1. Prepared statements with placeholders (?)
- Used in nearly all dynamic queries to prevent SQL injection and safely bind values.

2. Transactions
- Used in critical write paths:
  - signup
  - booking creation
  - payment processing
  - add-airline (+ aircraft rows)
- Pattern: beginTransaction -> execute multiple queries -> commit/rollback.

3. Row-level locking
- FOR UPDATE in booking/payment flows to enforce consistency under concurrency.

4. Join strategy
- INNER JOIN: requires matching related rows.
- LEFT JOIN: retains primary rows even with missing related records.
- This distinction directly affects empty-list bugs.

5. Aggregate queries
- COUNT, SUM, GROUP BY used for dashboards and analytics.

6. Runtime schema introspection
- SHOW COLUMNS to handle optional Booking.class column.

7. Manual key generation
- SELECT MAX(id)+1 used in Passenger/Flight paths.
- Works but is weaker than DB-native AUTO_INCREMENT/sequence under high concurrency.

====================================================
8) QUICK RISK/QUALITY NOTES (DBMS-SPECIFIC)
====================================================
- Duplicate route definitions in admin.js can cause unpredictable behavior and difficult debugging.
- Manual ID generation (MAX+1) can race under concurrency.
- Plaintext password checks in auth queries are functional but not secure for production.
- Some modules use uppercase table names and some lowercase; behavior depends on DB server/table name case settings.
