DETAILED FLOW: DBMS CONCEPTS, QUERIES, USAGE, PURPOSE, FRONTEND/BACKEND IMPACT, NORMALIZATION

Project: Airline Management System UI_UX
Database Type: Relational DBMS (MySQL)
Backend Stack: Node.js + Express + mysql2/promise connection pool
Frontend Stack: React + TypeScript

====================================================================
1) DBMS CONCEPTS USED IN THIS PROJECT
====================================================================

1.1 Relational Data Modeling
- Data is split into entities/tables such as Passenger, User, Airline, Aircraft, Airport, Flight, Booking, Payment, Booking_Seat.
- Relationships are formed using keys (primary keys and foreign keys).
- This allows consistency and reuse of data instead of storing everything in one large table.

1.2 Primary Key and Foreign Key Concepts
- Primary keys uniquely identify rows (for example passenger_id, flight_id, booking_id).
- Foreign keys link parent-child data:
  - Flight references Aircraft.
  - Aircraft references Airline.
  - Booking references Passenger and Flight.
  - Payment references Booking.
  - Booking_Seat references Booking and Flight.
- These relationships are used in SQL JOIN queries to compose final API payloads.

1.3 CRUD + Stateful Business Operations
- Create: register user, create airline/aircraft/airport/flight, create booking, create payment.
- Read: flight lists, bookings, payments, analytics, dashboard stats.
- Update: update airport, update flight, cancel booking, set status values.
- Delete pattern: mostly soft delete via status = INACTIVE or CANCELLED (not physical DELETE).

1.4 Soft Delete Pattern
- Instead of deleting row physically, status is changed:
  - airport.status = INACTIVE
  - flight.status = INACTIVE
  - booking.status = CANCELLED (in cancellation scenarios)
- Advantage:
  - historical data remains available
  - analytics and audit-style tracking remain possible
- Result:
  - frontend can still show historical records but with labels like Flight Cancelled/Refunded.

1.5 Transactions and Atomicity
- Booking flow uses transaction:
  beginTransaction -> checks -> inserts -> seat lock update -> commit
- Payment flow uses transaction:
  beginTransaction -> lock booking -> insert payment -> update booking status -> commit
- Signup flow (one route variant) also uses transaction.
- Purpose:
  - all related steps succeed together or fail together
  - avoids half-completed records.

1.6 Concurrency Control
- SELECT ... FOR UPDATE is used for lock-sensitive flows:
  - booking locks flight row before seat decrement
  - payment locks booking row before status update
- Purpose:
  - prevent race condition when two users act at same time.

1.7 JOIN-based Query Composition
- Rich API payloads are built through SQL JOINs across tables.
- Example: my bookings combines booking + flight + airport + aircraft + airline.
- Benefit:
  - one query returns all data needed for a frontend screen.

1.8 Aggregation and Analytics
- COUNT, SUM, GROUP BY are used in dashboards and admin analytics.
- Purpose:
  - produce KPIs (total bookings, total revenue, booking breakdown by airline/status).

1.9 Runtime Schema Introspection
- SHOW COLUMNS FROM Booking LIKE 'class' is used.
- Purpose:
  - supports deployment where Booking.class may or may not exist.
  - query path changes dynamically.

1.10 Connection Pooling
- mysql pool is used with connectionLimit and queueing.
- Purpose:
  - efficient connection reuse under multiple API calls.

====================================================================
2) CORE TABLES AND THEIR PURPOSE
====================================================================

2.1 Passenger
- Stores passenger identity and login information.
- Used by registration, login, bookings, dashboards.

2.2 User
- Used for admin login credentials.
- Login route first checks admin user table.

2.3 Airline
- Parent table for airlines.
- Contains airline name/code and status usage in business logic.

2.4 Aircraft
- Child table under airline.
- Stores aircraft model and seat distribution (economy/business/total).

2.5 Airport
- Stores airport code, name, city, terminal and status.
- Airport status drives route availability and cancellation cascade behavior.

2.6 Flight
- Central operational table linking source/destination airports and aircraft.
- Contains schedule, seat availability, fares and status.

2.7 Booking
- Stores booking master data per passenger per flight.
- Booking status changes through payment and cancellation flows.

2.8 Booking_Seat
- Junction/bridge table for booking-seat mapping (one booking can have many seats).
- Supports seat occupancy conflict detection.

2.9 Payment
- Stores payment records linked to booking.
- Payment status is converted to booking status.

--------------------------------------------------------------------
3A) DB CONNECTION / INFRASTRUCTURE
--------------------------------------------------------------------

Query pattern:
- connection.ping()

How and why:
- Runs during backend startup health check.
- Verifies DB is reachable before serving requests.

Backend effect:
- If ping fails: server startup stops.
- If ping succeeds: backend starts and routes are enabled.

Frontend effect:
- Indirect; frontend can only function when backend started successfully.

3B) AUTH AND REGISTRATION QUERIES
--------------------------------------------------------------------

B1) Email existence check
- SELECT email_id FROM passenger WHERE email_id = ?

How used:
- In register flow before insert.

Why/purpose:
- Prevent duplicate account creation.

Backend effect:
- Existing email -> response error.
- New email -> continue to insert path.

Frontend effect:
- Register page shows error message if email already exists.

B2) Passenger ID generation (manual)
- SELECT MAX(passenger_id) as max FROM passenger
or
- SELECT COALESCE(MAX(passenger_id), 0) + 1 AS next_passenger_id FROM Passenger

How used:
- Computes next passenger_id before insert.

Why/purpose:
- Table uses custom/manual id assignment strategy.

Backend effect:
- Generates new integer id.

Frontend effect:
- User can log in later using created account.

Risk note:
- MAX + 1 strategy can cause collisions in high-concurrency systems without stronger locking/auto-increment.

B3) Passenger insert
- INSERT INTO passenger (passenger_id, first_name, middle_name, last_name, email_id, phone_no, dob, passport_no, password) VALUES (...)

How used:
- Saves final registration record.

Why/purpose:
- Persist new user.

Backend effect:
- Account becomes available for login and booking.

Frontend effect:
- Register page navigates to login on success.

B4) Admin login check
- SELECT * FROM User WHERE email = ? AND password = ?

How used:
- First lookup in login route.

Why/purpose:
- Distinguish admin login from passenger login.

Backend effect:
- If found, returns role=admin object.

Frontend effect:
- Auth state becomes admin and protected admin pages open.

B5) Passenger login check
- SELECT * FROM Passenger WHERE email_id = ? AND password = ?

How used:
- Fallback when admin not found.

Why/purpose:
- Passenger authentication.

Backend effect:
- Returns role=passenger object.

Frontend effect:
- Passenger dashboard/features become available.

Security note:
- Current pattern uses plain password comparison in SQL.
- Production best practice: salted hash storage + app-level password verification.

D1) Passenger existence verification

How used:

Why/purpose:
- Ensure booking is for a valid user.

Backend effect:

How used:

- Backward compatibility across environments.

Backend effect:
- Chooses insert SQL variant dynamically.

Frontend effect:

D3) Flight seat lock
- SELECT available_seats FROM Flight WHERE flight_id = ? FOR UPDATE

How used:
- Inside booking transaction before seat insert.

Why/purpose:
- Lock row and prevent concurrent overbooking.

Backend effect:
- Guarantees available_seats check remains valid within transaction.

Frontend effect:
- Reduces chance of two users buying same final seats.

D4) Seat collision check
- SELECT seat_no FROM Booking_Seat WHERE flight_id = ? AND seat_no IN (...)

How used:
- Checks requested seats against existing reservations.

Why/purpose:
- Avoid duplicate seat assignment.

Backend effect:
- If conflict found -> 409 error with conflicting seat list.

Frontend effect:
- Payment step fails with meaningful message; user can reselect seats.

D5) Booking master insert
- INSERT INTO Booking (passenger_id, flight_id, amount, status, class?) VALUES (...)

How used:

Why/purpose:

Backend effect:

Frontend effect:

D6) Bulk booking-seat insert

Why/purpose:

Frontend effect:

D7) Seat inventory decrement

Frontend effect:

Frontend:

Backend:
- joins flight/aircraft/airline/airport with active flight filter.

Frontend:
- BookFlight requests booked seats for selected flight.
Backend:
- reads Booking_Seat seat list.
Outcome:

Frontend:
- sends booking payload, then payment payload.
Backend:
- transaction locks flight, checks seat conflicts, inserts booking, inserts seats, decrements available seats.

Outcome:
- success page on completion; failures return errors without partial data corruption.

4.6 Cancel Booking
Frontend:
- user clicks cancel.
Backend:
- booking status updated to CANCELLED.
Outcome:
- booking card switches to Cancelled state.

4.7 Admin Deletes Flight (Soft)
Frontend:
- admin clicks delete in ManageFlights.
Backend:
- sets flight INACTIVE, cancels related bookings.
Outcome:
- flight removed from active flight lists; affected bookings shown cancelled/flight-cancelled.

4.8 Admin Deletes Airport (Soft + Cascade)
Frontend:
- admin deletes airport.
Backend:
- airport INACTIVE -> related flights INACTIVE -> related bookings CANCELLED.
Outcome:
- airport hidden from active dropdowns; flights unavailable; impacted bookings marked cancelled.

5) WHY THESE QUERY TYPES ARE CHOSEN
====================================================================

- SELECT: read screens, validations, existence checks.
- INSERT: create master/transaction records (passenger, booking, payment, flight, etc).
- UPDATE: status changes, edits, soft delete behavior.
- JOIN: one API call returns complete denormalized response for UI.
- GROUP BY + COUNT/SUM: dashboard and analytics.
- FOR UPDATE + transaction: correctness in high-contention seat/payment operations.
- Runtime schema check: deployment compatibility when schema differs.

6) NORMALIZATION ANALYSIS (WHAT IS NORMALIZED AND HOW)
====================================================================

6.1 1NF (First Normal Form)
- Most tables hold atomic values per column (no repeated groups in one row).
- One concern:
  - airport.terminal appears to store comma-separated terminals (for example T1,T2,T3).
  - This is not ideal 1NF strictness because multiple values are in one column.
  - Better design: separate Airport_Terminal table.

6.2 2NF (Second Normal Form)
- Non-key columns in each table generally depend on full key.
- Booking_Seat behaves like a junction table for many seats per booking.
- If primary key is composite or surrogate plus unique combination, seat mapping is normalized enough for operational use.

6.3 3NF (Third Normal Form)
- Most transitive dependencies are split correctly:
  - Airline details are not duplicated in Flight; Flight references Aircraft then Airline.
  - Airport details are not copied into Flight beyond airport_code references.
- Reporting queries use JOINs instead of storing redundant denormalized strings.

6.4 Practical Denormalization for API Read Models
- API outputs include aliases (airline_name, source_city, destination_airport_name, etc).
- This is runtime denormalization by query, not table design denormalization.
- Good practice for frontend convenience.

6.5 Suggested Normalization Improvements
- Airport terminals:
  - Current: terminal string CSV in airport table.
  - Better:
    - Airport(airport_code, name, city, status)
    - Airport_Terminal(airport_code, terminal_code)
- Benefits:
  - easier terminal validation
  - cleaner JOIN filters
  - better data integrity.

6.6 Suggested Integrity Constraints (if not already in DB)
- Unique constraints:
  - Passenger.email_id unique
  - Airline.name unique (or case-insensitive unique handling)
  - Airline.code unique
  - Airport.airport_code unique
- Foreign keys with ON UPDATE/ON DELETE rules aligned with soft-delete logic.
- Optional check constraints:
  - economy_seats + business_seats = total_seats
  - available_seats >= 0
  - price and fare columns >= 0

7) IMPORTANT BEHAVIORAL NOTES FROM CURRENT CODE
====================================================================

- Soft delete is implemented through status fields, not hard DELETE for major operations.
- Some endpoints intentionally return active-only rows (for example flights and active-airports).
- Some master endpoints (like airlines and aircraft-by-airline) currently return broad rows without status filtering in current code.
- Manual id generation with MAX + 1 is used in some flows; this works functionally but is less safe under high concurrency than auto-increment/sequence.
- Password handling currently appears plaintext-based in DB comparison and should be upgraded to hashed auth for production.

8) CONCLUSION
====================================================================

This project uses core DBMS principles strongly:
- relational modeling,
- transactional correctness for booking/payment,
- soft delete lifecycle management,
- JOIN-based read models,
- aggregated analytics,
- and partial normalization with a few improvement opportunities.

9) HOW THE DATABASE IS CONNECTED PROPERLY IN THIS PROJECT
====================================================================

9.1 Connection Configuration Source
- The backend reads DB credentials from environment variables in backend/.env.
- In backend/db.js, dotenv loads .env using an absolute path based on the backend folder.
- Required variables:
  - DB_HOST
  - DB_USER
  - DB_PASSWORD
  - DB_NAME
  - DB_PORT (optional, defaults to 3306)

Why this is important:
- Credentials are not hardcoded in route files.
- Different environments (local/staging/production) can use different DB configs safely.

9.2 Connection Pool Creation
- backend/db.js creates one MySQL pool via mysql2/promise createPool with:
  - waitForConnections: true
  - connectionLimit: 10
  - queueLimit: 0

How this helps proper connection:
- Reuses open connections instead of opening new connection for every request.
- Prevents connection exhaustion during multiple simultaneous API calls.
- Handles queueing when demand is higher than active connection slots.

9.3 Startup Health Check (Verification Before Serving Requests)
- backend/server.js imports testConnection() from db.js.
- On server start, it runs testConnection() before app.listen().
- testConnection() flow:
  - gets a connection from pool
  - runs connection.ping()
  - releases connection in finally block

Purpose:
- Confirms DB is reachable and credentials are valid before the API is exposed.

Behavior:
- If ping succeeds: backend starts normally.
- If ping fails: startup catches error and exits process with failure.

9.4 Runtime Query Usage Pattern
- All route files import the same pool instance from db.js.
- Standard queries use:
  - pool.execute("SQL", [params])
- Transactional flows use:
  - const connection = await pool.getConnection()
  - beginTransaction()
  - connection.execute(...)
  - commit() or rollback()
  - connection.release() in finally

Why this is correct:
- Single shared pool avoids duplicate unmanaged connections.
- Transactional flows pin work to one connection, which is required for transaction correctness.
- finally release avoids connection leak.

9.5 Error Handling That Protects Connection Stability
- Startup-level DB errors stop server early, preventing partial app behavior.
- Route-level transaction blocks always rollback on error and release connection.
- Non-transaction queries rely on pool.execute, which is connection-managed by pool internals.

Impact:
- Keeps backend stable under failures.
- Avoids dangling/locked connections.

9.6 How to Confirm Connection Is Properly Working (Practical Checks)
- Check backend console at startup:
  - "Database connected successfully"
  - "Backend running at http://localhost:5000"
- Hit GET /health endpoint:
  - should return service health JSON.
- Trigger one DB-backed API (for example /flights):
  - should return rows without DB connection errors.

If connection fails, common causes:
- wrong DB_HOST / DB_USER / DB_PASSWORD / DB_NAME
- MySQL service not running
- DB user has insufficient privileges
- wrong DB_PORT or blocked port

9.7 Current Strength of This Connection Design
- Environment-based config
- Pooling enabled
- Pre-start connectivity test
- Safe transaction lifecycle (commit/rollback/release)

Overall result:
- The project connects to DB in a production-style, reliable pattern for small-to-medium traffic applications.
